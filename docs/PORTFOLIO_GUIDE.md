# Alyzyus: คู่มือเตรียมพอร์ตและซ้อมอธิบาย

ปรับเนื้อหาตาม feedback รุ่นพี่ วันที่ 7 พฤศจิกายน 2026

## ประโยคแนะนำโครงการ

Alyzyus เป็นต้นแบบร้านค้าออนไลน์ของร้านเดียวที่ขายได้หลายหมวด ลูกค้าเลือกสินค้า สั่งซื้อ ติดตามออเดอร์ และติดต่อร้าน ผู้ดูแลจัดการสินค้า สต็อก สถานะ และคำร้องผ่านข้อมูลชุดเดียวกัน

โครงการใช้โจทย์จำลองเพื่อฝึกการพัฒนาเว็บ ยังไม่มีข้อมูลยืนยันรายได้ จำนวนผู้ใช้จริง หรือผลประโยชน์ทางธุรกิจ ห้ามนำตัวเลขตัวอย่างไปอ้างเป็นผลงานจริง

## ลำดับเล่าเรื่องในสไลด์ใหม่

1. โครงการคืออะไร และมีขอบเขตเป็นร้านเดียว
2. โจทย์ที่ต้องแก้กับเป้าหมายการเรียนรู้
3. ผู้ใช้สองฝั่งและ Key Feature
4. ความถูกต้องของออเดอร์ การติดตาม และ Customer Service
5. Tech stack พร้อมเหตุผลที่เลือก
6. การแบ่ง Controller, Service และ Repository ใน checkout
7. Sequence Diagram ของการสั่งซื้อแบบเก็บเงินปลายทาง
8. ตัวอย่างสินค้าชิ้นสุดท้ายกับ row lock
9. ทดลอง /demo โดยไม่ใช้บัญชีจริง
10. หลักฐานทดสอบ ข้อจำกัด และสิ่งที่จะพัฒนาต่อ

สไลด์หลักมี 11 หน้า ส่วนอีก 3 หน้าเป็นภาคผนวกเรื่อง AI, UI และคำศัพท์ ใช้ตอบเมื่อกรรมการถาม ไม่จำเป็นต้องเปิดทุกหน้า บทพูดอยู่ใน Speaker Notes ของ PPTX และ [PRESENTATION_NOTES.md](PRESENTATION_NOTES.md)

## Flow ที่ควรอ่านโค้ดให้จบอย่างน้อยหนึ่งเรื่อง

เริ่มที่ `public/static/js/checkout.js` ซึ่งส่งข้อมูลไป `POST /api/checkout` จากนั้นดู:

- `server/api.py`: รับคำขอ ตรวจรูปแบบข้อมูล session และวิธีชำระเงิน
- `server/services/checkout.py`: เรียงขั้นตอน สร้าง fingerprint และเลือกผลลัพธ์การชำระเงิน
- `server/repositories/orders.py`: เรียก RPC และอ่านออเดอร์โดยจำกัดเจ้าของ
- `server/database.py`: ตัวรับส่ง HTTPS ไป Supabase
- SQL `create_order`: ตรวจราคาจริง คำนวณส่วนลด/ค่าส่ง ล็อกสินค้า และสร้างออเดอร์พร้อมลดสต็อกใน transaction

อ่าน [ARCHITECTURE.md](ARCHITECTURE.md) เพื่อดู Sequence Diagram แบบละเอียดและ flow ของคำร้องช่วยเหลือ Browser ไม่ได้ถือ server key และไม่ได้ยิง SQL โดยตรง การแบ่งชั้นช่วยลดการผูก route กับวิธีเก็บข้อมูล ส่วนกฎธุรกรรมยังอยู่ใน PostgreSQL เพื่อรักษาความถูกต้องร่วมกัน ไม่ได้อ้างว่าเปลี่ยนทุกโมดูลเป็น MVC เต็มรูปแบบแล้ว

## แบบฝึกที่ต้องลองเองก่อนนำเสนอ

1. วาดลูกค้า A และ B แย่งสินค้าที่เหลือ 1 ชิ้น อธิบายว่าใครถือ row lock และเมื่อไรปล่อยล็อก ลองเพิ่มกรณี A ล้มเหลวแล้ว rollback
2. อธิบายความต่างระหว่าง idempotency key กับ row lock โดยยกตัวอย่างเน็ตช้าจนกดปุ่มซ้ำ เทียบกับคนสองคนสั่งพร้อมกัน
3. แก้ราคาบนหน้าจอแล้วอธิบายว่าทำไมเซิร์ฟเวอร์ต้องอ่านราคาจริง อย่าใช้การซ่อนปุ่มเป็นระบบความปลอดภัย
4. อธิบาย RLS ด้วยตัวอย่างลูกค้าอ่านเฉพาะออเดอร์ของตัวเอง และผู้ดูแลมีสิทธิ์ต่างกัน
5. รัน `python scripts/check.py` แล้วเลือกอ่าน test ที่ปฏิเสธข้อมูลผิดอย่างน้อยหนึ่งกรณี จากนั้นลองแก้ fixture ในเครื่องและอ่านผลที่เปลี่ยน
6. เปลี่ยนเงื่อนไขเล็ก ๆ ในสภาพแวดล้อมทดสอบ อธิบายว่าจะต้องแก้ Controller, Service, Repository หรือ SQL เพราะอะไร

หากยังทำหรืออธิบายไม่ได้ ให้บอกว่าเป็นหัวข้อที่กำลังเรียนรู้ อย่าใช้ผลทดสอบที่ AI รันแทนหลักฐานว่าตนเข้าใจทุกบรรทัด

## สาธิตแบบปลอดภัย

เปิด [พื้นที่สาธิต](https://alyzyus.vercel.app/demo) แล้วเลือกสินค้า สร้างออเดอร์ตัวอย่าง สลับมุมมองผู้ดูแล อัปเดตสถานะ และกลับมาดูฝั่งลูกค้า ใช้ข้อมูลชั่วคราวในแท็บ ไม่มีเงินเข้าออก ไม่มีบัญชี Admin ใช้ร่วมกัน และไม่สร้างออเดอร์ในฐานข้อมูลจริง รายละเอียดอยู่ใน [DEMO.md](DEMO.md)

การสาธิตในเบราว์เซอร์แสดง UX และ flow เท่านั้น ไม่ได้ทดสอบ transaction หรือ RLS จริง ผล backend ใช้ชุดทดสอบแยก โหมดตัวอย่างไม่เปิดช่องเข้าถึงหลังบ้านจริง

ก่อนส่งพอร์ต ให้เปิดหน้าแรก /demo และลิงก์ GitHub จากหน้าต่างส่วนตัว พร้อมตรวจผ่านโทรศัพท์จริง หาก Supabase ขัดข้อง หน้าสาธิตต้องยังทำงานได้เมื่อแอป/เครือข่ายยังเข้าถึงได้ ส่วนหน้าร้านใช้ข้อมูลตัวอย่างแบบอ่านได้โดยแจ้งสถานะชัดเจน ไม่มีระบบ Cloud ใดรับประกันว่าเปิดได้ตลอดเวลาโดยไม่ดูแล ควรตรวจแผนบริการ โควตา การพักโปรเจกต์ และเตรียม PDF/ภาพสำรองด้วย

## การใช้ AI และที่มาของงาน

เปิดเผยว่าใช้ AI ช่วยร่าง UI, โค้ด, test และเอกสาร ผู้จัดทำกำหนดความต้องการและควรตรวจผลด้วยตัวเอง เก็บตัวอย่าง prompt ที่ไม่มีข้อมูลลับ รวมถึงเหตุผลที่รับหรือแก้ข้อเสนอของ AI ภาพ Hero เป็นภาพประกอบจาก AI ส่วนภาพหน้าจอเป็นภาพจากโปรแกรม อ่านที่มาใน `ASSETS.md`

ไม่ใส่คีย์ลับ รหัสผ่าน หรือข้อความลูกค้าใน prompt, สไลด์ หรือ public repository ไม่อ้างว่าเขียนทุกบรรทัดเองหรือเข้าใจส่วนที่ยังไม่ได้ศึกษา

## ขอบเขตที่ต้องพูดให้ตรง

- ร้านเดียวหลายหมวด ไม่ใช่ marketplace หลายผู้ขาย
- Customer Service เป็นคำร้องและบทสนทนา ไม่ใช่พนักงานแชตสดตลอด 24 ชั่วโมง
- ภาพ 3D แสดงขั้นตอนจากสถานะที่บันทึก ไม่ใช่ GPS หรือสถานะที่เปลี่ยนเองตาม animation
- PWA ติดตั้งได้ตามความสามารถเบราว์เซอร์ ยังไม่ได้หมายความว่าเป็น native app ใน App Store/Play Store
- การรับเงินจริง การคืนเงิน SMTP นโยบายร้าน และความปลอดภัยบัญชี Cloud ต้องตั้งค่าและตรวจแยก
- ผลตรวจผ่านกรณีทดสอบที่เขียนไว้ ไม่ใช่การรับรองว่าไม่มีช่องโหว่หรือรับโหลดได้ทุกระดับ

ตัดเรื่องแบบจำลองคิวสำนักงานและ Poisson ออกจากเรื่องเล่าในพอร์ตนี้ เพราะไม่ได้ช่วยอธิบายร้านค้าออนไลน์
