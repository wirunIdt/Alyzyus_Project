## คำแนะนำโครงการ

Alyzyus เป็นเว็บร้านค้าหลายหมวดหมู่ที่รวมหน้าร้าน บัญชีลูกค้า ระบบคำสั่งซื้อ และหลังบ้านไว้ด้วยกัน ใช้ Python Flask เป็นเซิร์ฟเวอร์กับ HTML CSS JavaScript ฝั่งเบราว์เซอร์ ข้อมูลคำสั่งซื้อเก็บใน Supabase PostgreSQL และเผยแพร่เว็บบน Vercel

จุดที่นำเสนอเป็นผลงานทางวิศวกรรมได้คือการตรวจราคาและตัดสต็อกในธุรกรรมเดียว การแบ่งสิทธิ์ลูกค้าและผู้ดูแล รวมถึงการอธิบายขั้นตอนสินค้าในฉาก 3D ที่ใช้ทรัพยากรเครื่องอย่างจำกัด แบบจำลองคิวสำนักงานช่วยทดลองผลของจำนวนเจ้าหน้าที่และอัตราคนเข้าโดยไม่แก้ข้อมูลร้านจริง

โครงการพัฒนาร่วมกับเครื่องมือ AI จากข้อกำหนดของผู้จัดทำ AI ช่วยเขียนโค้ด ปรับ UI สร้างภาพหลัก และจัดชุดตรวจสอบ ควรอธิบายกระบวนการนี้ตามจริง พร้อมสาธิตความเข้าใจโค้ดและการแก้ไขด้วยตนเองก่อนใช้สัมภาษณ์ ไม่อ้างว่าเขียนทุกบรรทัดเองหรือมีลูกค้าและรายได้จริง

## สถานะผลงาน ณ 16 ตุลาคม 2569

- เว็บและฐานข้อมูลเชื่อมกันแล้ว สมาชิกสมัคร ยืนยันอีเมล และเข้าสู่ระบบได้
- หน้าร้านมี 3 ภาษา 2 ธีม ถุงสินค้า การกรอง และรายการโปรด
- ระบบสร้างคำสั่งซื้อจากราคาที่ฐานข้อมูลกำหนด และป้องกันการกดสั่งซ้ำ
- ผู้ดูแลจัดการสินค้า คำสั่งซื้อ การชำระเงินแบบตรวจเอง และเลขพัสดุได้
- อัปโหลดรูปจากเครื่อง ย่อภาพก่อนส่ง Supabase Storage และสร้างคำแปลจากภาษาหลักเดียวผ่าน MyMemory ได้ โดยตรวจแก้คำแปลก่อนเผยแพร่
- ภาพเส้นทางสินค้าอ้างอิงสถานะคำสั่งซื้อที่ผู้ใช้มีสิทธิ์อ่าน ไม่มี GPS สด
- รุ่น QC วันที่ 16 ตุลาคม 2026 ผ่านชุดทดสอบ Python 55 กรณี และ Node 41 กรณี รวม 96 กรณี พร้อม lint, formatter, syntax และ template checks
- การตรวจ Supabase security advisor หลัง hardening ไม่พบรายการเตือนในขอบเขตที่เครื่องมือตรวจ
- สินค้าตัวอย่างในฐานข้อมูล 8 รายการเป็น draft และสต็อก 0 จึงยังไม่เปิดขายสินค้าเหล่านี้
- เก็บเงินปลายทางเปิดอยู่ ส่วนบัตร PromptPay และโอนธนาคารรอข้อมูลผู้ให้บริการและบัญชีร้าน

ผลการทดสอบเป็นหลักฐานเฉพาะกรณีที่ตรวจ ไม่ใช่การรับประกันว่าไม่มีข้อผิดพลาดหรือรองรับผู้ใช้จำนวนมากแล้ว ยังไม่มีผล load test ภาคสนามหรือข้อมูลผู้ใช้จริง

## ลำดับสาธิต 5 ถึง 7 นาที

1. เปิดหน้าเว็บ อธิบายผู้ใช้สองกลุ่มและปัญหาที่ระบบจัดการ สลับภาษาและ Light/Dark
2. เปิด `/admin` ด้วยบัญชีเจ้าของ แสดงสินค้า draft และชี้ว่าการเผยแพร่ต้องมีข้อมูลร้านจริง ห้ามทำธุรกรรมหรือเพิ่มสต็อกหลอกเพื่อสาธิตบน Production
3. อธิบายถุงสินค้าและตรวจราคาฝั่งเซิร์ฟเวอร์ ใช้โหมดตัวอย่างในเครื่องหรือโปรเจกต์ทดสอบแยกหากต้องการทดลองคำสั่งซื้อ
4. เปิด `/simulation?mode=product` อธิบาย 5 ขั้นตอนและป้าย DEMO จากนั้นอธิบายว่าออเดอร์จริงอ่านจาก API ที่ตรวจสิทธิ์
5. เปิด `/simulation` เพิ่มอัตราคนเข้าและเจ้าหน้าที่ตรวจเอกสาร ดูคิวในฉาก หมุนอาคาร และหยุดชั่วคราว แบบจำลองใช้เวลาสุ่ม จึงไม่ควรอ้างผลจากครั้งเดียวเป็นข้อสรุปทางสถิติ
6. เปิดโครงสร้าง `server/` และ SQL migrations อธิบายธุรกรรม RLS และ idempotency จากโค้ดจริง
7. แสดงผลทดสอบ ข้อจำกัด และสิ่งที่จะพัฒนาต่อ

## คำถามที่ควรเตรียมตอบ

**เหตุใดใช้ Flask**
โครงการต้องการ Python และหน้าเว็บที่ไม่ต้องมีขั้นตอน build ฝั่งลูกค้า Flask เหมาะกับ API และ Jinja templates ขนาดนี้ การเลือก Flask ไม่ได้พิสูจน์ว่าเร็วที่สุดในทุกงาน ควรวัด latency และภาระงานจริงก่อนเปลี่ยนสถาปัตยกรรม

**ป้องกันราคาที่แก้จากเบราว์เซอร์อย่างไร**
เบราว์เซอร์ส่งรหัสสินค้าและจำนวน เซิร์ฟเวอร์ตรวจข้อมูล แล้ว SQL function คำนวณราคา คูปอง ค่าจัดส่ง และล็อกสินค้าเพื่อสร้างออเดอร์กับลดสต็อกในธุรกรรมเดียว

**เหตุใดมี RLS แม้ API ตรวจสิทธิ์แล้ว**
RLS เป็นข้อจำกัดในฐานข้อมูลสำหรับการเข้าถึงด้วยสิทธิ์ผู้ใช้ API ตรวจ session และบทบาทด้วย ขณะที่ server key เก็บใน environment เฉพาะเซิร์ฟเวอร์ ต้องไม่ส่งไปหน้าเว็บหรือ GitHub

**การจำลองตรงกับโลกจริงเพียงใด**
ใช้ Poisson arrivals และเวลาบริการสุ่มรอบค่าเฉลี่ยเพื่อศึกษาคิว ยังไม่ได้ปรับเทียบกับข้อมูลสำนักงานจริง ค่าผลลัพธ์จึงเป็นการทดลองตามพารามิเตอร์ ไม่ใช่คำทำนายเวลารอจริง

**ทำไม 3D ไม่ทำให้เครื่องหนักมาก**
ใช้รูปทรงง่ายและ instancing จำกัดภาพตัวละคร 80 ตัว จำกัดสำนักงาน 30 FPS และเส้นทางสินค้า 18 FPS กับ pixel ratio พักเมื่อแท็บซ่อน จำนวนคนเชิงตรรกะยังนับทุกคน การใช้ทรัพยากรจริงขึ้นกับอุปกรณ์ จึงยังต้องทดสอบบนเครื่องเป้าหมาย

**อะไรยังไม่พร้อมเปิดร้าน**
สินค้าและรูปจริง บัญชีรับเงิน SMTP นโยบายผู้ขาย และการทดสอบรับเงินคืนเงินในสภาพแวดล้อมแยก ต้องทำก่อนเปิดรับลูกค้าจริงเต็มรูปแบบ

## หลักฐานใน repository

`tests/test_backend.py` ตรวจ session สิทธิ์ input และ webhook `tests/database.test.mjs` ตรวจธุรกรรมและ RLS บน PostgreSQL จำลองสำหรับพัฒนา `tests/queue3d.test.mjs` ตรวจการคงจำนวนคน การออกจากอาคาร การลดเจ้าหน้าที่ และสิทธิ์ดูออเดอร์

คู่มือใช้และแก้โค้ดอยู่ใน `README.md` `CODE_GUIDE.md` และ `supabase/OPERATIONS.md` ใบแนะนำและสไลด์ที่ส่งให้ควรอ่านและปรับคำพูดให้เป็นภาษาของผู้สมัครก่อนนำเสนอ


## ความสามารถที่เพิ่มวันที่ 15 ตุลาคม 2026

เพิ่ม PWA พร้อมหน้าแนะนำติดตั้งสำหรับ Android/iOS/macOS และเว็บเบราว์เซอร์ที่รองรับ, ปุ่มสมัครบัญชีที่เห็นชัด, การเลือกโทนสี 6 แบบ/ธีม/ขนาดตัวอักษร/การเคลื่อนไหว และรูปพื้นหลังที่เก็บเฉพาะอุปกรณ์ เพิ่ม Activity Log ที่ตรวจสิทธิ์ Admin และเก็บประวัติการเปลี่ยนสินค้า สต็อก ออเดอร์แบบ transaction เดียวกับฐานข้อมูล

เพิ่ม GitHub Actions ที่ไม่ใช้คีย์ Production สำหรับตรวจธุรกรรม/RLS และการไม่แคชข้อมูลส่วนตัวใน PWA ตรวจ layout ผ่านเบราว์เซอร์ที่ความกว้าง 280, 390, 768, 1024 และ 1440 พิกเซล และตรวจภาษา/ธีม/การเก็บรูปพื้นหลัง ไม่อ้างว่าได้ทดสอบกับโทรศัพท์จริงทุกรุ่นหรือผ่านการอนุมัติ App Store/Google Play

เอกสาร PDF และสไลด์ที่จัดทำก่อนหน้านี้เป็นภาพรวมของรุ่นเดิม ใช้คู่กับ README และคู่มือนี้เมื่ออธิบายฟีเจอร์ล่าสุด อ้างเฉพาะผลงานและผลทดสอบที่ทำได้จริง
