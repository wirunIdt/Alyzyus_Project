# บทพูดและการซ้อมนำเสนอ Alyzyus

ฉบับ 7 พฤศจิกายน 2026 มีเนื้อหาหลัก 11 สไลด์และภาคผนวก 3 สไลด์ ใช้เวลาพูดประมาณ 6–8 นาที ไม่จำเป็นต้องเปิดภาคผนวกทุกหน้า

## สไลด์ 1: โครงการนี้คืออะไร

25 วินาที: Alyzyus เป็นเว็บร้านค้าออนไลน์ของร้านเดียว ขายสินค้าได้หลายหมวด ไม่ใช่ marketplace ที่หลายร้านมาเปิดร้านแข่งกัน โจทย์นี้ใช้ฝึกการพัฒนาเว็บตั้งแต่หน้าจอจนถึงการจัดเก็บคำสั่งซื้อ ผมกำหนดความต้องการและใช้ AI ช่วยพัฒนาต้นแบบ เนื้อหาต่อไปจะแยกสิ่งที่ระบบจริงทำกับส่วนสาธิตให้ชัด

แหล่งตรวจสอบ: README.md; ภาพประกอบแบรนด์จาก AI ตาม ASSETS.md

## สไลด์ 2: Objective: solving และ learning

35 วินาที: ผมใช้โจทย์ร้านค้าจำลอง ไม่ได้อ้างว่าร้านจริงสูญเสียออเดอร์เป็นจำนวนเท่าไร สิ่งที่อยากแก้คือข้อมูลราคาและสต็อกไม่ตรงกัน การส่งคำสั่งซื้อซ้ำ และการสื่อสารสถานะ ส่วนที่อยากเรียนรู้คือ API การแบ่งสิทธิ์และการทดสอบ ผลที่ประเมินตอนนี้จึงเป็นพฤติกรรมของโปรแกรม ไม่ใช่ยอดขาย

แหล่งตรวจสอบ: server/validation.py; server/api.py; tests/database.test.mjs

## สไลด์ 3: Feature ของแต่ละฝั่ง

35 วินาที: ลูกค้าเข้าถึงเฉพาะคำสั่งซื้อและคำร้องของตัวเอง ผู้ดูแลมีสิทธิ์จัดการสินค้าและสถานะของร้าน ฟีเจอร์ภาษาและธีมช่วยเรื่องการอ่าน แต่แกนของโครงการคือคำสั่งซื้อที่ถูกต้องและการติดตามได้ การติดตั้งปัจจุบันเป็น PWA ไม่ใช่แอป native ที่ลง App Store แล้ว การแต่งสีและพื้นหลังของร้านจริงต้องเป็นสมาชิกที่ยืนยันอีเมล

## สไลด์ 4: ความถูกต้องของคำสั่งซื้อ

40 วินาที: เบราว์เซอร์ส่งรหัสสินค้าและจำนวน ไม่ส่งราคาที่ระบบต้องเชื่อถือ เซิร์ฟเวอร์ใช้ RPC อ่านราคาจริง กฎค่าจัดส่งและส่วนลด แล้วสร้างออเดอร์กับลดสต็อกใน transaction เดียว ถ้าผิดพลาดให้ย้อนทั้งหมด idempotency key คือรหัสระบุคำขอเดิม การ retry ด้วยรหัสเดิมจึงคืนออเดอร์เดิม ส่วน payload ที่แก้แต่ใช้รหัสเดิมจะถูกปฏิเสธ ตรงนี้ต่างจากการล็อกแถวสินค้า

## สไลด์ 7: สถาปัตยกรรมที่ใช้จริง

45 วินาที: นี่คือ Layered Architecture ที่แยกความรับผิดชอบคล้าย MVC ไม่ได้อ้างว่าเปลี่ยนทุกไฟล์เป็น MVC เต็มรูปแบบ View คือหน้าจอ Controller รับ HTTP และตรวจสิทธิ์ Service เรียงขั้นตอนธุรกิจ Repository รู้วิธีเรียก Supabase ข้อมูลจากเบราว์เซอร์ผ่าน API ไม่เชื่อมฐานข้อมูลโดยตรง การแก้ครั้งนี้แยกเส้นทาง checkout ออกจริง ส่วนโมดูลอื่นยังค่อย ๆ แยกได้ การมี SQL function ไม่ได้ทำให้ระบบผิดโดยตัวมันเอง เพราะงานราคาและสต็อกต้องทำแบบ atomic ในฐานข้อมูล

แหล่งตรวจสอบ: server/api.py; server/services/checkout.py; server/repositories/orders.py; server/database.py; docs/ARCHITECTURE.md

## สไลด์ 8: Flow ของระบบจริง

50 วินาที: อ่านจากบนลงล่าง เริ่มที่เบราว์เซอร์ส่ง POST ไป API API ตรวจรูปแบบข้อมูล session และวิธีชำระเงิน จากนั้น Service สร้าง fingerprint และ Repository เรียก RPC ผ่าน Supabase Data API PostgreSQL ตรวจราคา ล็อกสินค้า สร้างออเดอร์กับลดสต็อก เมื่อ transaction สำเร็จจึง commit และคืนเลขออเดอร์ API อ่านข้อมูลออเดอร์ส่ง JSON ให้หน้าเว็บ Diagram ย่อชั้น Service/Repository และ Auth เพื่อให้อ่านง่าย COD ไม่ได้แปลว่าลูกค้าชำระเงินแล้ว ถ้าสต็อกไม่พอหรือ session ไม่ผ่านจะตอบ error แทนเส้นสำเร็จ

แหล่งตรวจสอบ: server/api.py checkout; server/services/checkout.py; server/repositories/orders.py; docs/ARCHITECTURE.md; หมายเหตุ: /demo จำลองเส้นทางนี้ในหน่วยความจำ ไม่เรียก RPC

## สไลด์ 9: Row lock ต่างจากการล็อกทั้งฐานข้อมูล

45 วินาที: คำว่า lock database ใน feedback ให้ผมอธิบายให้แม่นขึ้นว่าโค้ดใช้ SELECT FOR UPDATE กับแถวสินค้า พร้อมเรียงลำดับสินค้าเพื่อลด deadlock เมื่อ A ถือ lock B รอ A commit สต็อกเหลือศูนย์ B จึงอ่านค่าที่อัปเดตแล้วและถูกปฏิเสธ ถ้า A ผิดพลาด rollback จะไม่หักสต็อกค้าง และ B สามารถดำเนินการต่อได้ สินค้าคนละแถวยังทำงานได้ตามชนิดล็อกที่เกี่ยวข้อง รูปนี้เป็นตัวอย่างเพื่ออธิบายกลไก ไม่ใช่ผล load test ของระบบ

แหล่งตรวจสอบ: supabase/migrations/202610110001_commerce.sql create_order; https://www.postgresql.org/docs/current/explicit-locking.html#LOCKING-ROWS

## สไลด์ 14: คำศัพท์และตัวอย่างสำหรับซ้อมตอบ

ก่อนนำเสนอให้ทดลองเอง: 1) เปลี่ยน quantity ให้มากกว่าสต็อก แล้วอธิบายว่าทำไมต้องปฏิเสธ 2) ยกตัวอย่างเน็ตช้ากดซ้ำว่า idempotency key ช่วยอย่างไร 3) วาด A กับ B แย่งสินค้าชิ้นสุดท้ายว่า row lock ต่างจากการซ่อนปุ่มบน UI อย่างไร 4) เปรียบเทียบ RLS กับการซ่อนเมนู Admin ถ้ายังอธิบายไม่ได้ให้กลับไปอ่าน code path ในคู่มือ คำตอบควรเป็นความเข้าใจของตนเอง ไม่ใช่ท่องนิยามบนสไลด์
