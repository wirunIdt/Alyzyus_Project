# ศูนย์บริการลูกค้า Alyzyus

ลูกค้าเข้าสู่ระบบและยืนยันอีเมลก่อนส่งคำถามได้ที่ `/support` ผู้ดูแลตอบจาก `/admin/support` ระบบเก็บบทสนทนาใน Supabase โดยไม่ส่งข้อความออกไปยังอีเมลหรือบริการแชตภายนอก และไม่มีบอตแอบอ้างเป็นเจ้าหน้าที่

## การใช้งาน

1. ลูกค้าเลือกหมวดคำสั่งซื้อ การชำระเงิน คืนสินค้า สินค้า บัญชี หรือเรื่องอื่น
2. กรอกหัวข้อ 5–120 ตัวอักษร และข้อความ 10–4,000 ตัวอักษร สามารถผูกคำสั่งซื้อของตนเองได้
3. เรื่องใหม่มีสถานะ `open` ผู้ดูแลตอบแล้วเป็น `pending` (รอลูกค้า) ลูกค้าตอบกลับเป็น `open`
4. ลูกค้าหรือผู้ดูแลเลือกแก้ไขแล้วเป็น `resolved` ลูกค้ายังตอบหรือเปิดเรื่องเดิมต่อได้
5. ผู้ดูแลปิดเป็น `closed` บทสนทนาจะอ่านได้อย่างเดียว ผู้ดูแลเท่านั้นที่เปิดเรื่องที่ปิดแล้วกลับมาได้ ลูกค้าสามารถสร้างเรื่องใหม่ได้

ไม่มีการรับประกันเวลาตอบ ไม่ได้แสดงว่ามีเจ้าหน้าที่ออนไลน์ ไม่มีอัปโหลดไฟล์แนบและการคืนเงินจริงอัตโนมัติ หมวดคืนสินค้าใช้รับเรื่องให้ผู้ดูแลตรวจสอบเท่านั้น ข้อความใหม่จะเห็นเมื่อกดรีเฟรชหรือเปิดเรื่องอีกครั้ง

## API

- `GET /api/support/tickets?limit=20&cursor=<id>&status=all|open|pending|resolved|closed`
- `POST /api/support/tickets` รับ `{category,subject,message,orderId:null|UUID,idempotencyKey:UUID}` คืน `{ticket}`
- `GET /api/support/tickets/<id>?limit=40&cursor=<message-id>` คืน `{ticket,messages,nextCursor,hasMore,limit}`
- `POST /api/support/tickets/<id>/messages` รับ `{message,idempotencyKey}` คืน `{ticket,message}`
- `PATCH /api/support/tickets/<id>` รับ `{action:'resolve'|'reopen'}`
- ผู้ดูแลใช้เส้นทาง `/api/admin/support/tickets` แทนและเพิ่ม action `close` ได้ ไม่มี POST สร้างเรื่องแทนลูกค้า

รายการและข้อความเรียงตาม ID ล่าสุดก่อน ใช้ keyset pagination สูงสุด 100 รายการต่อครั้ง ID แบบ bigint ส่งเป็น string เพื่อไม่เสียเลขเมื่อผ่าน JavaScript ระบบไม่ส่ง fingerprint หรือ idempotency key ออกมาในรายละเอียดเรื่อง

## การป้องกันข้อมูล

- Auth service ตรวจบัญชีและยืนยันอีเมลทุก request ที่ต้องใช้สิทธิ์ ไม่เชื่อ role จาก browser หรือ `user_metadata`
- อ่านด้วย JWT ของผู้ใช้และ RLS: ลูกค้าเห็นเฉพาะเรื่องของตน ผู้ดูแลเห็นทั้งหมด
- Client roles มีสิทธิ์ SELECT เท่านั้น ไม่สามารถเพิ่ม แก้ไข หรือลบตารางโดยตรง และเรียก write RPC ไม่ได้
- Write RPC เป็น `SECURITY INVOKER` เปิดให้ `service_role` เท่านั้น ตรวจ owner คำสั่งซื้อและ role ของผู้ดูแลซ้ำจากตาราง profiles
- ลูกค้าสร้างไม่เกิน 5 เรื่องต่อชั่วโมงและส่งข้อความรวมข้อความแรกไม่เกิน 20 ข้อความต่อชั่วโมง ผู้ดูแลที่ตอบผ่านเส้นทางเจ้าหน้าที่ตอบได้สูงสุด 200 ข้อความต่อชั่วโมง เพื่อรองรับการบริการหลายลูกค้า ใช้ advisory lock และข้อมูลจริงใน transaction จึงใช้ร่วมกันได้แม้มีหลาย server instance
- ลูกค้าเปลี่ยนสถานะได้ไม่เกิน 30 ครั้งต่อชั่วโมงต่อบัญชี ผู้ดูแลผ่านเส้นทางเจ้าหน้าที่ได้สูงสุด 200 ครั้งต่อชั่วโมง การ retry สถานะเดิมเป็น no-op ไม่เพิ่ม audit เพื่อป้องกันการสลับสถานะสร้าง log จำนวนมาก การใช้เส้นทางลูกค้าไม่เพิ่มเพดานแม้บัญชีนั้นเป็น Admin
- UUID idempotency ป้องกันการส่งซ้ำกรณี network retry ข้อมูลเดิมคืนผลเดิมก่อนตรวจ quota ถ้าใช้ key เดิมกับข้อมูลต่างกันคืน `IDEMPOTENCY_CONFLICT`
- Origin, same-site และ JSON guards ใช้เหมือน API เดิม ข้อความต้องแสดงเป็น text ไม่ใช่ HTML
- Audit เก็บเฉพาะ ticket ID, หมวด, สถานะ และ role ผู้ตอบ ไม่คัดลอกชื่อเรื่อง ข้อความ อีเมลหรือข้อมูลติดต่อ
- บทสนทนาอยู่ในฐานข้อมูลหลัก ไม่รวมลงไฟล์ Public/GitHub ไม่เพิ่มสิทธิ์ guest ให้เข้าถึงข้อมูล
